# تقرير المطابقة القانونية الذكية (AI Legal Matcher)

- **التاريخ:** 2025-11-02
- **المُعد:** GitHub Copilot
- **النطاق:** توثيق الواقع الحالي لميزة المطابقة القانونية الذكية المخصصة للمدققين في منصة AuditOrbit بهدف تقييم الجاهزية وتحديد فجوات التكامل.

---

## 1. المسار والموقع

- **المسار الفعلي:** المكون موجود داخل صفحة المدقق العامة `frontend/app/auditor/page.tsx` ولا يملك Route مستقل؛ يتم تفعيل العرض عبر الحالة الداخلية `activeView === "compliance"`. [المرجع: `frontend/app/auditor/page.tsx`]
- **مسار الوصول:**
  1. دخول المدقق إلى `/auditor`.
  2. اختيار مهمة → الانتقال إلى عرض "تفاصيل المهمة".
  3. الضغط على الزر "المطابقة القانونية الذكية" الذي يستدعي `setActiveView("compliance")`. [المرجع: `frontend/app/auditor/page.tsx` (زر عند خطوط ~640-650)]
- **ملاحظة:** لا يوجد مسار منفصل من نوع `/auditor/legal-matcher`; التحويل يتم داخل الصفحة نفسها عبر تغيير الحالة.

## 2. المكونات التقنية (الحالة الحالية)

- **نماذج الذكاء الاصطناعي:** غير موجودة في التطبيق التشغيلي؛ يتم إعداد نتائج مطابقة وهمية (`mockComplianceResults`) داخل الواجهة دون الاتصال بأي نموذج حقيقي. [المرجع: `frontend/app/auditor/page.tsx` (تعريف النتائج الوهمية عند خطوط ~130-175)]
- **قاعدة البيانات القانونية:** لا توجد جداول أو ملفات بيانات في الإنتاج الحالي. المستودع يخلو من ملفات JSON/SQL خاصة بالقوانين. وثيقة التخطيط (`doc/تقرير العمل/INTERNAL_AUDIT_COMPREHENSIVE_REPORT.md`) تقترح جداول مثل `legal_references` لكنها غير منفذة في الـ migrations.
- **مكتبات البحث الدلالي:** لم يتم دمج FAISS/Chroma/غيرها في الكود الحالي. لا يوجد استدعاء لأي مكتبة بحث متجهي.
- **واجهات الـ API:** لا يوجد Endpoint للذكاء الاصطناعي؛ البحث في مجلد `api/app/presentation/routers` يخلو من مسار `/compliance` أو مكافئ. وظيفة `handleSearchCompliance` لا تجري أي طلب HTTP بل تستخدم `setTimeout` لإرجاع النتائج الوهمية.

## 3. بيانات القوانين والمحتوى

- **المصدر:** غير موجود فعليًا. الوثيقة المعمارية المقترحة تشير إلى نية فهرسة القوانين القطرية ضمن "Legal documents embeddings"، لكن لم يتم توفير ملف مصدر أو سكربت للاستيراد.
- **حجم البيانات:** لا توجد بيانات فعلية؛ الأرقام المذكورة ("أكثر من 1000 مادة") واردة في تقارير التصميم فقط ولم تُخزن في النظام.
- **هيكل التخزين المقترح:** الوثيقة (`INTERNAL_AUDIT_COMPREHENSIVE_REPORT.md`) تقترح تخزين نتائج المطابقة في جدول `legal_references` مرتبط بـ `findings`. عدم وجود الهجرة يدل على أن التخزين الفعلي لم يُنفذ بعد.

## 4. خوارزمية المطابقة (الوضع الحالي)

- **حساب الدرجات:** القيم مثل 92.3% أو 78.5% مضمنة يدويًا داخل `mockComplianceResults`. لا يوجد منطق حقيقي لحساب التشابه.
- **معايير التصنيف:** يتم تعيين الملصقات (🟢 قوية / 🟡 متوسطة / ⚪ مراجعة) وفق الحقل المسمى `level` في النتائج الوهمية. الدالة `getSimilarityColor` و `getSimilarityLabel` تمثل التدرج اللوني لكن تعتمد على القيمة الثابتة `level`. [المرجع: `frontend/app/auditor/page.tsx` (الدوال عند خطوط ~210-250)]
- **البحث الدلالي:** غير متوفر حاليًا. الاقتراح النظري (توليد embedding ثم البحث في vector DB) موثق في المستندات فقط.

## 5. الواجهة والمكونات

- **المكونات الرئيسة:**
  - Textarea لإدخال النص (`Textarea` من `@/components/ui/textarea`).
  - حقول إعدادات عدد النتائج وحد الدقة (`Input`).
  - زر تنفيذ البحث يشغل `handleSearchCompliance` ويعرض مؤشر تحميل بسيط (`Loader2`).
  - قائمة النتائج تعرض `Badge` للتصنيف وأزرار "عرض المادة" و"حفظ كدليل"، جميعها تعمل على الحالة المحلية فقط. [المرجع: `frontend/app/auditor/page.tsx`]
- **التصميم:** يعتمد على شريط تدرج لوني وBadges؛ جميع الأنماط من Tailwind.
- **التصدير والحفظ:** زر "توليد تقرير" ينقل المستخدم إلى عرض "report-generation" ويملأ حقولًا ثابتة؛ لا يتم حفظ ملف أو إرسال طلب Backend.
- **لقطات شاشة:** لا توجد لقطات مخزنة في المستودع. يلزم التقاط صور من نسخة التطبيق لتلبية المتطلبات.

## 6. سير العمل الفعلي

1. إدخال نص في Textarea.
2. الضغط على زر البحث.
3. يتم تفعيل `setIsSearching` لمدة 1.5 ثانية (`setTimeout`).
4. يتم عرض النتائج الوهمية المحفوظة مسبقًا.
5. يمكن للمستخدم تفعيل زر "حفظ كدليل" الذي يضيف المعرف إلى مصفوفة `savedMatches` في الحالة المحلية؛ لا يحدث أي طلب API أو كتابة لقاعدة البيانات.
6. اختيار "توليد تقرير" يعبئ بيانات ثابتة ويحول العرض دون تكامل خارجي.

- **زمن الاستجابة:** ثابت (1.5 ثانية) بغرض المحاكاة وليس قياسًا حقيقيًا للأداء.
- **آلية حفظ الأدلة:** غير موجودة. لا يتم إنشاء سجل في `evidence` أو `findings` ولا استدعاء لـ `/ai/extract`.

## 7. حالة التكامل

- **تشغيل فعلي:** الميزة تعمل كـ Proof-of-Concept UI فقط. لا يوجد تكامل Backend أو وظيفة ذكاء اصطناعي حقيقية.
- **الأخطاء المعروفة:** غياب endpoint يجعل الإجراء غير فعّال؛ لا يتم التحقق من صحة المدخلات أو معالجة أخطاء الشبكة.
- **التكامل مع التقارير:** زر "توليد تقرير" لا يتصل بوحدة التقارير؛ النتيجة تبقى داخل الحالة المحلية.

## 8. البيانات الفنية المرتبطة

- **الجداول الفعلية في قاعدة البيانات:**
  - `evidence`, `evidence_extractions` موجودة وتُستخدم في مسار OCR، لكن لا يتم ربطها بالمطابقة القانونية ضمن الكود الحالي. [المرجع: `api/app/presentation/routers/evidence.py`, `ai/worker/ocr.py`, `ai/worker/tasks.py`]
  - `legal_references` غير موجود فعليًا في الهجرات.
- **Endpoints متاحة حاليًا:**
  - `/ai/extract/{evidence_id}` و`/ai/extractions` لمعالجة الأدلة النصية (OCR). [المرجع: `api/app/presentation/routers/ai.py`]
  - لا يوجد `/compliance/match` أو ما شابه.
- **نماذج البيانات المستخدمة في الواجهة:**
  - النتائج الوهمية عبارة عن كائنات `{ id, law, article, similarity, level, excerpt }` معرفة داخل `mockComplianceResults`.
  - لا يوجد TypeScript type مخصص؛ يتم استخدام `any[]`.

## خلاصة تحليلية

**حالة الميزة:** الهيكل الحالي عبارة عن واجهة تجريبية دون منطق ذكاء اصطناعي فعلي. جميع البيانات ثابتة داخل الواجهة، ولا توجد طبقات خدمة أو بيانات داعمة.

**الفجوات الأساسية:**

1. عدم وجود مصدر بيانات للقوانين أو Vector Store.
2. غياب API خاص بالمطابقة القانونية.
3. عدم ارتباط النتائج بالأدلة أو بالتقارير في قاعدة البيانات.

## توصيات أولية للتطوير

1. **تأسيس طبقة بيانات قانونية:** إنشاء جدول/مستودع (PostgreSQL + JSON أو Vector DB) واستيراد المواد القانونية.
2. **توحيد نموذج البيانات:** تعريف TypeScript types و DTOs في Backend للتعامل مع نتائج المطابقة.
3. **تطوير خدمة مطابقة:** بناء خدمة FastAPI (`/compliance/match`) تعتمد على نموذج embedding (مثل `sentence-transformers`) مع مخزن متجهي (FAISS أو Qdrant).
4. **ربط النتائج بالأدلة:** عند الحفظ، إنشاء سجل في `legal_references` مرتبط بـ `findings` و/أو `evidence`.
5. **تحسين الواجهة:** إضافة مؤشرات حالة متصلة بالـ API، وتمكين تصدير النتائج وإدراجها في تقارير التدقيق.
6. **توثيق وسائط:** التقاط لقطات شاشة رسمية وإضافتها لمجلد `deepseek-report/screenshots/` أو مكافئ.

> **ملحوظة:** هذه الوثيقة تعكس الوضع الحالي في المستودع (`master` بتاريخ 2025-11-02). أي تطوير لاحق يجب أن يُحدث التقرير لمطابقة الواقع الجديد.

## 2. الأنماط المتكررة

- **الصفحات:**
  - بنية موحدة تعتمد على تقسيم واضح حسب الدور (`/admin`, `/manager`, `/auditor`, `/ops`).
  - جميع المسارات ثابتة بدون معرّفات ديناميكية؛ كل قسم يحتوي صفحة جذر + صفحات وظيفية فرعية متشابهة (CRUD، إعدادات، تقارير).
  - تشابه قوي في مسارات الإدارة (Users/Roles/Engagements/Reports) يقترح إمكانية إنتاج مكوّنات مشتركة للبطاقات والجداول.

- **واجهات البرمجة:**
  - معظم المجموعات تتبع نمط CRUD كامل (GET/POST/PUT/DELETE) مع endpoint إضافي للحالات الخاصة (مثل `/reports/{id}/approve`).
  - إعادة استخدام نفس نمط المسار الأساسي (`/api/<resource>`)، ما يسهل توليد SDK أو أتمتة الوثائق.
  - وجود Endpoints توثيقية (`/docs`, `/redoc`, `/openapi.json`) يتيح البناء الآلي للعقود.

- **جداول قاعدة البيانات:**
  - علاقات كثيرة إلى كثير عبر جداول وصل (`user_roles`, `role_permissions`, `engagement_team`).
  - الاعتماد المركزي على جدول `engagements` كمحور يربط الخطط، القوائم، المستندات، الفرق، مما يعكس نموذج عمل متسق.

## 3. مؤشرات التعقيد غير الضروري

- **مسارات المستخدم:**
  - تعدد الواجهات لكل دور مع غياب مسارات ديناميكية قد يؤدي إلى تكرار في التنقل؛ يمكن دمج صفحات فرعية عبر tabs بدل صفحات منفصلة حين تكون الوظائف متقاربة (مثال: `/admin/reports` مقابل `/manager/reports`).

- **طبقة الـAPI:**
  - حسب `reports/initial-assessment.md`، تعتمد الـrouters على SQL خام دون طبقة خدمات، وRBAC معطّل عمليًا. هذا يرفع التعقيد التشغيلي ويخلق مخاطر أمنية دون قيمة مضافة.
  - وجود 35 Endpoint CRUD قد يضخم الكود المتكرر (تحقق، ترحيل DTO)، ما يستدعي توليد مخطط موحد أو اعتماد طبقة Service/Repository.

- **هيكل البيانات:**
  - جداول RBAC مزدوجة (role_id في users + جدول user_roles) تشير إلى ازدواجية بنيوية؛ يلزم تقرير ما إذا كان سيتم الاعتماد على عمود واحد أو جدول وصل فقط.
  - جدول `settings` يحمل JSONB عامًا، لكنه يشير إلى ثغرة حوكمة إن لم تُفرض بنية واضحة.

## 4. توصيات فورية (أسبوع التنفيذ الأول)

1. **إعادة تفعيل الحماية الأساسية:**
   - توصيل `security/rbac.py` ببيانات الصلاحيات الفعلية أو وضع Gate بديل (حتى لو مبسط) لضمان احترام الأدوار الثلاثة الأساسية.

2. **تنظيف المسارات المتشابهة:**
   - دمج واجهات التقارير والإشعارات المشتركة بين Admin/Manager في مكوّنات مشتركة مع تفرقة صلاحيات من خلال الحماية بدلاً من صفحات منفصلة.

3. **إنشاء طبقة خدمة موحدة:**
   - استخراج عمليات CRUD المتكررة (Users، Engagements، Reports) إلى طبقة `application/services` لتقليل التكرار وتمهيد الاختبارات.

4. **تحديد ملكية الجداول المزدوجة:**
   - حسم استخدام `role_id` الفردي مقابل `user_roles` متعدد القيم؛ في حال الاحتفاظ بالإثنين يجب توثيق قاعدة التزامن أو إزالة أحدهما.

5. **لوحة مراقبة مصغرة:**
   - استغلال `/ops` لبناء لوحة أداء مبسطة تعرض عدد الطلبات الناجحة/الفاشلة خلال الأسبوع، تمهيدًا لجمع بيانات استخدام الصفحات لاحقًا.

| اليوم | المهمة | المخرجات |

| الإثنين | استخراج خدمات CRUD للمستخدمين والمشاريع من routers | وحدات خدمة + واجهات محدثة تعتمدها |

| السبت | جلسة تثبيت (stabilization) واختبارات تكامل + تحديث الوثائق | تقرير اختبار سريع + تحديث `preliminary-diagnostic` بالنتائج |

## 6. أولويات التحليل المتعمق لاحقًا

1. **تحليل التفاعل مع المهام التدقيقية:** فهم دورة حياة `engagements` بالكامل، بما في ذلك `followups`, `findings`, `reports`.
2. **قياس الأداء والتحميل:** غياب سجلات أداء حالية يفرض تشغيل اختبارات `frontend/tests/performance.spec.ts` وتوثيق نتائج زمن الاستجابة.
3. **تحليلات الاستخدام:** إعداد تتبع لزيارة الصفحات والمزايا (GA4 أو بديل ذاتي) لمعرفة المسارات المهجورة.
4. **توحيد الوثائق:** ربط ERD النصي بمخطط بصري وتوليد OpenAPI محدث لتسهيل التعاقد مع الفرق الأخرى.
5. **مراجعة أمنية متخصصة:** بعد تفعيل RBAC، إجراء مراجعة أعمق للتوثيق والسرية (secrets management، صلاحيات S3، تسجيل الأحداث).

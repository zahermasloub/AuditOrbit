## 1. تحليل الصفحات المتكررة (Deep Page Analysis)

### 1.1 قياس التشابه الوظيفي

| المجال | الصفحة | نظير مشابه | نسبة التداخل التقديرية | الملاحظات |
|--------|--------|-------------|-------------------------|------------|
| Admin | `/admin/reports` | `/manager/reports` | 0.85 | كلاهما يعرض قوائم تقارير مع إجراءات موافقة/عرض؛ الاختلاف الرئيسي في مستوى الصلاحية. |
| Admin | `/admin/engagements` | `/manager/engagements` | 0.8 | نفس عمليات CRUD على engagements مع اختلاف محدد في حقول التحكم. |
| Admin | `/admin/checklists` | `/auditor/checklists` | 0.75 | تشابه في عرض قوائم التحقق، لكن واجهة المدقق تركز على التنفيذ بينما الإدارة تركز على الإعداد. |
| Admin | `/admin/audit-log` | `/ops/logs` | 0.7 | كلاهما يعرض سجلات ونشاطات، لكن `/ops/logs` أوسع (يشمل النظام). |
| Manager | `/manager/reports` | `/auditor/archive` | 0.6 | كلاهما يعرض تقارير نهائية، لكن المدقق يطّلع على الأرشيف بينما المدير يراجع التقارير النشطة. |

### 1.2 توصيات دمج الصفحات

1. **دمج `/admin/reports` و`/manager/reports`** عبر مكوّن موحد يعرض المحتوى بصلاحيات مشروطة (conditional rendering). يقلل التكرار ويضمن اتساق تجربة المستخدم.
2. **تقريب `/admin/engagements` و`/manager/engagements`** عبر لوحة واحدة مع اختلاف في الأزرار حسب الدور (مثل تمكين الموافقة للمدير فقط).
3. **إنشاء صفحة موحدة لسجلات النظام** تربط `/admin/audit-log` و`/ops/logs` ضمن واجهة واحدة تسمح بالفلترة حسب مصدر السجل.

### 1.3 صفحات منخفضة القيمة

| الصفحة | الملاحظة | الإجراء المقترح |
|--------|----------|-----------------|
| `/debug-token` | موجهة للتطوير فقط؛ لا تضيف قيمة إنتاجية. | نقلها إلى مسار تطوير محمي أو إزالتها من الإصدار النهائي. |
| `/ops/ai` | تخطيط وظيفي دون بيانات حالياً. | تأجيل نشرها أو دمجها مع لوحة `/ops` الرئيسية لحين اكتمال الوظائف. |

## 2. تحليل واجهات البرمجة (API Duplication Analysis)

### 2.1 تقييم التداخل

| مجموعة API | Endpoints | مجموعة مشابهة | نسبة التداخل | الملاحظات |
|-------------|-----------|----------------|---------------|------------|
| `/api/reports` | CRUD + Approve | `/api/manager/reports` في واجهات داخلية | 0.9 | نفس المنطق تقريبًا؛ يمكن توحيد العمليات مع أذونات مختلفة. |
| `/api/engagements` | CRUD | `/api/manager/engagements` (ضمن routers متفرقة) | 0.8 | تكرار في إدارة الفريق والحقول؛ دعم عمليات خاصة عبر معلمات بدلاً من مسارات جديدة. |
| `/api/checklists` | CRUD بنود | `/api/auditor/tasks` | 0.7 | استدعاءات المدقق تعتمد نفس البيانات مع فلتر مختلف. |
| `/api/evidence` | رفع/حذف ملفات | `/api/ops/storage` (في خطة مستقبلية) | 0.6 | يمكن توحيد إدارة الملفات عبر طبقة خدمة واحدة. |
| `/api/users` | CRUD | `/api/auth/me`, `/api/admin/users` | 0.6 | بيانات المستخدم موزعة؛ توحيد الردود في Resource موحد. |

### 2.2 توصيات التبسيط

- **توحيد إدارة التقارير**: دمج جميع استدعاءات `/reports` في خدمة واحدة مع معلمة دور أو حالة لتجنب ازدواج المسارات.
- **اعتماد `engagement_service`**: حصر جميع عمليات المشاريع في طبقة خدمة تستقبل دور المستدعي وتطبق قواعد العمل بدل تكرار الاستعلامات.
- **استخدام DTO موحد لـ`User`**: توفير مخططات استجابة/طلب مشتركة تقلل إعادة تعريف الحقول في كل Endpoint.
- **ترشيد Endpoints التوثيقية**: نشر `/openapi.json` فقط واستخدامه لتوليد `api-client`، مع إبقاء `/docs` و`/redoc` للأغراض الداخلية دون تكرار.

### 2.3 كفاءة استهلاك الموارد

- الاستعلامات الحالية تعتمد SQL خام بدون caching؛ يوصى بإضافة طبقة تخزين مؤقت بسيط (Redis) للأرقام الإجمالية المعروضة في لوحات المعلومات.
- نقل عمليات رفع الملفات إلى مهام خلفية إن تجاوزت الحمل المتوقع لتخفيف الضغط عن API.

## 3. تحليل قاعدة البيانات المتعمق

### 3.1 الجداول والعلاقات الزائدة

| الجدول | الملاحظة | التوصية |
|--------|----------|----------|
| `users.role_id` + `user_roles` | وجود عمود مباشر وجداول وصل يعكس تصميمين متوازيين. | اختيار أحد النموذجين (single-role أو multi-role) وتعديل البنية تبعًا لذلك. |
| `role_permissions` | لا يستخدم فعليًا مع تعطيل RBAC الحالي. | إما تفعيله أو إزالة الاعتماد وتوثيق السبب. |
| `ai_jobs` | غير مدمج في أي مسارات حالية. | تقييم الحاجة؛ إما ربطه بالواجهات أو تجميده حتى يتم تفعيل خدمة AI. |
| `settings` (JSONB) | تخزين عام بدون مخطط؛ يعقّد الاستعلامات. | تفكيك الإعدادات الحرجة إلى جداولtyped أو إضافة قيود على JSON schema. |

### 3.2 تكرار البيانات

- بيانات المستخدم تتكرر عبر جداول `audit_logs`, `engagement_team`, `checklist_items` (أعمدة `user_id`). يوصى بإعداد View موحد لـ"هوية المستخدم" لتقليل الانضمامات المتكررة.
- `engagements` يرتبط بخطط سنوية ووثائق وفِرَق؛ يجب التأكد من تحديث `progress` و`status` في جدول واحد لتجنب التناقض.

### 3.3 الفهارس والاستعلامات

- معظم الجداول تعتمد Primary Keys فقط. يُنصح بإضافة فهارس على الأعمدة المتكررة في WHERE مثل `status`, `assigned_to`, `engagement_id`.
- الاستعلامات خام داخل الـrouters؛ يوصى بتوثيق الاستعلامات الأعلى تكلفة وتشغيل خطة تنفيذ (EXPLAIN) لتحديد حاجة الفهارس الإضافية.

## 4. تحليل سير العمل (Workflow Complexity)

### 4.1 تدفق عمليات رئيسي: دورة حياة التقرير

```text
Auditor ➜ /auditor/tasks ➜ /api/checklists (تنفيذ المهام)
  ➜ /api/evidence (رفع مستندات)
  ➜ /api/reports (إنشاء تقرير أولي)
Manager ➜ /manager/reports (مراجعة)
  ➜ /api/reports/{id}/approve (اعتماد)
Admin ➜ /admin/reports (إشراف نهائي + أرشفة)
``` 

**ملاحظات:**
- التنقل يتم عبر صفحات منفصلة لكل دور؛ يمكن تحسينه باستخدام لوحة مشتركة تعرض حالة المهمة حسب الدور.
- نقاط الاختناق: الموافقة تعتمد على Endpoint منفصل، ما يضيف خطوة إضافية؛ يمكن استبداله بحالة قابلة للتغيير ضمن نفس Endpoint.

### 4.2 تبسيط المسارات

- **إنشاء لوحة موحدة للتقارير**: تبويب متعدد (قائمة المدقق، انتظار المدير، أرشيف المدير/المدير الفني) مع فلترة مبنية على الدور.
- **ربط الصفحات بالعمليات**: إضافة روابط مباشرة من `/admin/engagements` إلى `/admin/reports` لتقليل الانتقال اليدوي.

### 4.3 مسار المستخدم لعمليات المستخدمين

```text
Admin ➜ /admin/users ➜ /api/users (CRUD)
  ➜ /api/auth/me (تأكد من الصلاحيات)
Manager/Auditor ➜ /dashboard ➜ طلب صلاحيات ➜ فشل بسبب RBAC المعطل
```

- الحاجة إلى بوابة موحدة تمنع مستخدمين بدون صلاحيات من الوصول قبل إعادة تفعيل RBAC.

## 5. تحليل تكرار الصلاحيات (Permission Redundancy)

### 5.1 مقارنة الأدوار الحالية

| الصلاحية | Admin | Manager | Auditor | ملاحظات |
|----------|:-----:|:-------:|:-------:|----------|
| `engagements:read` | ✔ | ✔ | ✔ | يمكن دمجها بصلاحية مشتركة مع مستويات وصول مختلفة (scoped). |
| `engagements:write` | ✔ | ✔ | ✖ | يصعب الفصل في حال الاعتماد على نفس الواجهات؛ يجب ضبطها عبر RBAC حقيقي. |
| `reports:read` | ✔ | ✔ | ✔ (أرشيف فقط) | المستثمر: يجب فصل `reports:view_all` عن `reports:view_assigned`. |
| `reports:approve` | ✔ | ✔ | ✖ | المدقق لا يحتاج لها؛ يمكن تقييدها لدور واحد لتقليل التعقيد. |
| `checklists:execute` | ✖ | ✖ | ✔ | خاصة بالمدقق؛ لا تكرار. |
| `ops:full_access` | ✔ | ✖ | ✖ | صلاحية وحيدة؛ يمكن تفكيكها لصلاحيات أصغر (logs، storage، ai) لتفويض أدق. |

### 5.2 توصيات تبسيط نظام الصلاحيات

1. **اعتماد مستويات وصول (Scopes)** بدل تعريف صلاحيات لكل دور من الصفر. مثال: `reports:view`، `reports:manage`.
2. **تجميع الصلاحيات المتشابهة** مثل `users:read` و`roles:read` تحت Bundle إداري واحد.
3. **إزالة الصلاحيات المعطّلة** (`role_permissions` بدون استخدام) أو ربطها بنظام enforcement فعلي.
4. **توليد مصفوفة RBAC آلية** من قاعدة البيانات وإدراجها في الوثائق لضمان المزامنة مع الكود.

## 6. النتائج المرقمة والمتطلبات

### 6.1 الصفحات الموصى بدمجها

1. `/admin/reports` + `/manager/reports` – دمج في صفحة تقارير موحدة مع فلترة حسب الدور.
2. `/admin/engagements` + `/manager/engagements` – واجهة إدارة واحدة مع أزرار/أعمدة ديناميكية حسب الدور.
3. `/admin/audit-log` + `/ops/logs` – لوحة سجلات واحدة تدعم أنواع الأحداث المختلفة.
4. `/ops/ai` دمج مع لوحة `/ops` الرئيسية حتى اكتمال الوظائف.

### 6.2 واجهات البرمجة المرشحة للإزالة/الدمج

1. Duplicate CRUD في `/api/reports` مقابل أي routers مخصصة للمدير – توحيد في خدمة واحدة.
2. عمليات `/api/engagements` المتفرعة – دمج endpoints الخاصة بالمدير ضمن نفس المجموعة مع معاملات إضافية.
3. Endpoints بحت التطوير (`/debug-token`, API helpers) – نقلها إلى بيئة تطوير أو تعطيل في الإنتاج.
4. استدعاءات غير محمية (`/audit-logs` مع RBAC معطل) – يجب إما حماية أو إزالتها مؤقتًا.

### 6.3 الجداول والعلاقات الزائدة

1. `users.role_id` مقابل `user_roles` – اختيار نموذج واحد.
2. `role_permissions` بدون تفعيل – إما إعادة تشغيله أو إزالته.
3. `ai_jobs` – تجميد أو ربط مع ميزة محددة.
4. `settings` (JSONB) – تنظيمه أو تفكيكه حتى لا يتحول لمستودع غير مضمن.

### 6.4 خطة إعادة هيكلة سير العمل

1. **أسبوع 1:** دمج صفحات التقارير، توحيد واجهات التقارير، إعداد RBAC بسيط.
2. **أسبوع 2:** إنشاء خدمات أعمال (`engagement_service`, `report_service`)، نقل الاستعلامات من routers.
3. **أسبوع 3:** تحسين قاعدة البيانات (إزالة التكرار، إضافة فهارس)، تفعيل تتبع الأداء.
4. **أسبوع 4:** إطلاق لوحة مراقبة `/ops` وتحسين تجربة المستخدم للتنقل بين الأدوار.

- **اليوم 1:** إعداد قائمة الصفحات المدمجة وتحديث مسارات Next.js لتستخدم مكونات مشتركة.
- **اليوم 2:** دمج Endpoints التقارير والمشاريع ضمن خدمات مشتركة، وإعادة تفعيل RBAC الأساسي.
- **اليوم 3:** مراجعة بنية قاعدة البيانات، تنفيذ migration لتبسيط جداول RBAC، وإضافة توثيق لتدفق العمل المحدث.

> التحليل يعتمد على الوثائق المتوفرة؛ عند تنفيذ الخطوات المقترحة يجب تحديث التقارير وقياس الأثر (زمن الاستجابة، عدد الاستدعاءات، نسبة الأخطاء) لضمان نجاح إعادة الهيكلة.

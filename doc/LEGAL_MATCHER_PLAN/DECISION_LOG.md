## القرارات المسجلة

### 1) التوثيق الآن والتأجيل المنظّم للتنفيذ
- التاريخ: 2025-10-28
- المالك/أصحاب المصلحة: فريق منصة التدقيق الداخلي (Internal Audit Platform Team)
- السياق/المشكلة:
  - طلب المستخدم اعتماد وضع "توثيق الآن للتنفيذ لاحقًا" بدل البدء الفوري بالتطبيق العملي، مع توفير مواد تشغيلية مكتملة عند اتخاذ قرار التنفيذ.
- البدائل:
  - البدء الفوري بتنفيذ البنية التحتية والخدمات والدمج (legal-matcher + Qdrant + API + Frontend).
  - تجهيز بيئة GPU وتفعيل تسريع النموذج.
  - إضافة رصد/لوحات Prometheus وDashboards من البداية.
- القرار:
  - توثيق كامل قابل للتنفيذ لاحقًا دون تعديل الكود الآن.
  - إضافة حزمة وثائق مساندة: Runbook Checklist، Environment Vars، Template JSONL، PowerShell Quick Start.
- المبررات:
  - تقليل المخاطر والتغييرات المبكرة قبل توحيد بيانات القوانين (Corpus) واعتماد عتبات التصنيف وموضع اللوحة UI.
  - إتاحة نافذة مراجعة داخلية للسياسات والصلاحيات (RBAC) ومتغيرات البيئة.
- التأثيرات/المخاطر:
  - لا تغييرات في الكود حاليًا؛ التنفيذ عند الطلب سيكون أسرع بسبب توثيق الخطوات.
  - المتطلبات عند التنفيذ: Docker Desktop (WSL2)، منافذ 8000/8001/6333، ملف corpus بصيغة JSONL (≥ 1000 فقرة)، متغيرات البيئة مضبوطة.
  - أول تشغيل يحتاج اتصال إنترنت لتنزيل النماذج (ما لم يُجهّز Cache مسبقًا).
- إجراءات التنفيذ والمتابعة:
  - تجهيز/مراجعة ملف `laws_qatar.jsonl` النهائي.
  - إكمال متغيرات البيئة حسب `ENVIRONMENT_VARS.md`.
  - اختيار موضع لوحة الواجهة LegalMatcherPanel (صفحة Engagement أو Sandbox).
  - اعتماد عتبات التصنيف (0.85 قوي، 0.70–0.85 متوسط، أقل من 0.70 راجع يدويًا) أو تعديلها.
- الحالة: مفتوح – للتنفيذ عند طلب المضي قدمًا.

### 2) تمكين GPU لتسريع التضمين/البحث

- التاريخ: 2025-10-28
- المالك/أصحاب المصلحة: فريق المنصة + البنية التحتية
- السياق/المشكلة:
  - استخدام BGE-M3 وعمليات الفهرسة/الاستعلام على CPU مناسب للتطوير المحلي، لكن قد يصبح بطيئًا عند أحجام بيانات أكبر أو متطلبات زمنية أدق.
- البدائل:
  - تشغيل CPU فقط (افتراضي حاليًا).
  - تمكين GPU (CUDA مع بطاقات NVIDIA) داخل حاويات Docker.
- القرار:
  - الإبقاء على CPU كافتراضي للتبسيط والتوافق.
  - تمكين GPU عند توافر عتاد مناسب واحتياج واضح للأداء (قرار لاحق).
- المبررات:
  - قابلية التشغيل على كل الأجهزة بدون تعقيدات تعريفات/درايفرات.
  - تقليل مخاطر بناء صور ضخمة ومتطلبات NVIDIA ضمن مرحلة التوثيق.
- التأثيرات/المخاطر:
  - مع GPU: ضرورة توافق نسخة الدرايفر مع CUDA، زيادة حجم الصور، تعقيد في إعدادات Docker (runtime: nvidia)، واحتمالات مشاكل ذاكرة.
- إجراءات التنفيذ والمتابعة (عند التفعيل):
  - اختيار صورة أساس CUDA مناسبة (مثل nvidia/cuda:12.x-runtime-ubuntuXX).
  - تثبيت torch/cuDNN المتوافقة مع CUDA.
  - تعيين `DEVICE=cuda` مع سقوط تلقائي إلى `cpu` إذا لم تتوفر CUDA (`torch.cuda.is_available()`).
  - إضافة دعم GPU في docker-compose (nvidia runtime/DeviceRequests بحسب نسخة Docker).
  - اختبار الأداء قبل/بعد لضبط دفعات المعالجة والذاكرة.
- الحالة: معلّق – يُفعّل عند الحاجة والتوافر العتادي.

### 3) الرصد والمقاييس (Prometheus/Grafana)

- التاريخ: 2025-10-28
- المالك/أصحاب المصلحة: فريق المنصة + التشغيل
- السياق/المشكلة:
  - الحاجة إلى رؤية زمن الاستجابة ومعدلات الطلبات والأخطاء عند التشغيل الفعلي، دون زيادة تعقيد مبكر.
- البدائل:
  - الاكتفاء بسجلات JSON وهيكلية فقط (حاليًا).
  - إضافة Prometheus (جمع مقاييس) + Grafana (لوحات) منذ البداية.
- القرار:
  - الاكتفاء مرحليًا بسجلات JSON وهيكلية وواجهات Docs.
  - تأجيل Prometheus/Grafana لمرحلة لاحقة مع خطة واضحة.
- المبررات:
  - تقليل التعقيد المبكر والتركيز على إثبات الوظائف والأداء الأساسي.
- التأثيرات/المخاطر:
  - صعوبة تحليل مشاكل الأداء بدون مقاييس مفصلة إذا ظهرت مبكرًا.
- إجراءات التنفيذ والمتابعة (عند التفعيل):
  - إضافة مكتبة مثل `prometheus-fastapi-instrumentator` إلى خدمة legal-matcher وفتح مسار `/metrics`.
  - توسيع docker-compose بإضافة خدمات prometheus وgrafana مع ضبط سكربتات scrape.
  - إنشاء لوحات أولية لزمن الاستجابة K=5، معدل الأخطاء، ومعدل الفهرسة.
- الحالة: مؤجل – يُفعّل عند الاقتراب من بيئة شِبه إنتاجية.
